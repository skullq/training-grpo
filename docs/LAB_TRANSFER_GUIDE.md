# 신규 L2/STP 랩 테스트 검증 항목

## 검증 대상과 현재 상태

- [신규 20문제](../data/lab-transfer/scenarios_v1.json)의 사전 조건, 정답 후보 및 모델 응답이 실제 랩에서 요구 사항을 만족하는지 검증합니다.
- 자료는 **미승인·미검증 초안**입니다. 사람 리뷰와 랩 검증은 아직 수행하지 않았으며 모델 응답도 생성하지 않았습니다.
- [배선/베이스라인](../data/lab-transfer/topology_and_baseline.md)을 초기 상태의 기준으로 사용합니다.
- 실제 결과는 [빈 결과 양식](../data/lab-transfer/results_template.json)에 기록합니다.

## 1. 초기 상태와 문항 재현성

- 운영망과 분리된 격리 랩인지 확인합니다.
- A/B/C 노드의 배선, 대상 포트와 관리 인터페이스가 문항의 전제와 일치하는지 확인합니다.
- VLAN, 트렁크, STP 모드, 우선순위 및 포트 설정이 베이스라인과 일치하는지 확인합니다.
- 각 문항의 사전 설정과 전제 조건이 실제로 성립하는지 확인합니다.
- 정답 후보를 먼저 검증해 문항 자체가 재현 가능한지 확인합니다. 정답 후보 결과와 모델 결과는 구분합니다.
- 미지원 기능, 잘못된 정답 후보 또는 성립하지 않는 초기 상태는 `blocked`로 기록합니다. 이를 모델 실패로 집계하지 않습니다.

## 2. 후보 응답의 적합성과 CLI 수락

- 모델 응답에서 실행할 명령을 정상적으로 추출할 수 있는지 확인합니다. 추출 불가는 형식 오류로 기록합니다.
- 지정된 대상 노드와 포트에만 변경을 요청하는지 확인합니다.
- 관리 접속, 인증, 설정 저장, 재시작 또는 전체 초기화 등 요구 밖 변경이 포함된 위험 후보는 실행하지 않고 `blocked`와 이유를 기록합니다.
- 실제 장비에서 구문 오류, 불완전한 명령, 모호한 명령, 거부 또는 값 범위 오류가 발생하는지 확인합니다.
- 모델의 원본 후보를 기준으로 평가합니다. 사람이 수정한 후보의 성공을 원래 모델의 성공으로 기록하지 않습니다.
- **CLI 오류가 없다는 사실만으로 목표 달성을 성공으로 판정하지 않습니다.**

## 3. 요구 설정과 보존 조건

- 각 문항의 검증 조건에 따라 VLAN, STP 모드, 루트 우선순위, 경로 비용, 포트 우선순위 및 Guard 설정이 요구 값과 대상에 적용됐는지 확인합니다.
- 실제 구성과 STP 상태를 함께 확인합니다. 화면에 표시되는 우선순위는 VLAN 확장 값을 포함할 수 있으므로 구성값과 구분합니다.
- 변경하지 말아야 할 VLAN, 포트, 우선순위와 관리 설정이 유지되는지 확인합니다.
- 장비 전체에 영향을 주는 모드 변경은 다른 VLAN에 미치는 영향도 확인합니다.
- 허용된 대체 명령은 실제 효과와 보존 조건으로 판단합니다. 정답 후보와 명령 순서가 다르다는 이유만으로 실패 처리하지 않습니다.

## 4. 실제 동작과 수렴

- 요구한 루트 브리지, 루트 포트, 지정 포트, 대체/차단 포트 상태가 형성되는지 확인합니다.
- 일시적인 상태만 보고 성공 처리하지 않고, 사전에 정한 관찰 간격과 제한 시간 내에 목표 상태가 안정적으로 유지되는지 확인합니다.
- 관찰 간격과 제한 시간, 적용 전후 상태 및 시간 초과 여부를 기록합니다. 시간 초과를 자동 성공으로 처리하지 않습니다.
- BPDU Guard는 승인된 시험 링크에서 BPDU 수신 후 오류 차단 상태와 원인을 확인합니다.
- Root Guard는 superior BPDU 수신 시 루트 불일치 차단 상태와 자극 제거 후 복구를 확인합니다.
- Loop Guard는 링크를 유지하면서 BPDU 수신이 중단되는 조건에서 검증합니다. 단순 링크 종료는 기능 검증으로 인정하지 않습니다.
- 기능 재현 방법이 준비되지 않았으면 `functional_status`를 `not_run`으로 기록합니다.
- 장애 주입이나 추가 노드 변경은 승인된 격리 랩에서만 수행합니다.

## 5. 원복과 시험 독립성

- 매 후보는 동일한 베이스라인과 해당 문항의 사전 조건에서 평가합니다.
- 시험 후 A/B/C 및 추가로 변경한 모든 노드가 초기 상태로 복구됐는지 확인합니다.
- 설정뿐 아니라 포트와 STP 상태도 복구됐는지 확인하고 증거를 기록합니다.
- 원복 실패 시 다음 후보 시험을 중단합니다. 이전 시험의 변경이 다음 결과에 섞이지 않도록 합니다.

## 6. 결과 판정

| 항목 | 검증 내용 |
|---|---|
| `setup_status` | 베이스라인, 사전 설정 및 전제 조건 성립 |
| `cli_status` | 원본 후보의 CLI 수락 |
| `required_settings_status` | 요구 값과 대상에 설정 적용 |
| `preservation_status` | 변경 금지 설정 유지 |
| `functional_status` | 실제 동작 및 복구 확인 |
| `rollback_status` | 모든 변경 노드의 원복 확인 |

상태는 `not_run`, `pass`, `fail`, `blocked`, `not_applicable`로 구분합니다.
미실행 항목의 시간과 점수는 빈 값으로 유지하고 성공처럼 기록하지 않습니다.

- 초기 상태, CLI, 필수 설정, 보존 조건 및 원복이 모두 통과하면 **설정 수준의 성공**으로 기록할 수 있습니다.
- 필수 기능 목표가 있는 문항은 실제 기능까지 통과해야 최종 성공입니다. 기능 미실행이면 최종 상태는 `blocked`입니다.
- 설정만 확인한 결과와 기능까지 확인한 결과는 각각 `configuration_only`, `functional_verified`로 구분합니다. 기능 미검증 결과를 기능 성공률에 포함하지 않습니다.
- 환경 문제로 차단된 시험은 모델 정답률 분모에서 제외하되 제외 건수와 이유를 함께 보고합니다.
- 적용 전후 및 원복 증거, 장비 이미지/버전, 시나리오 버전, 후보 종류와 모델 식별 정보를 보존합니다. 민감정보가 포함된 원본 증거는 로컬에 보관합니다.

기존 [실장비 검증 스크립트](../scripts/run_live_lab_validation_v2.py)는 이 신규 suite의 모든 목표 상태와 보존 조건을 검증하지 않으며 원복 실패 시 중단을 보장하지 않습니다. 해당 스크립트의 CLI 오류 검사 결과만으로 이 테스트의 최종 성공을 판정하지 않습니다.
